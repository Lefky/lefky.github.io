# Project Instructions

- Work on `dev` or a new branch. Do not push unless the user explicitly asks.
- Use OpenSpec for feature changes: record the behavior and scenarios, implement against the change, validate it, and archive it when complete.
- Before implementing a change, get the user's explicit approval of its OpenSpec proposal and design. Update those artifacts in response to feedback and do not begin implementation until approval is clear.
- Treat a PR merge into `master` as a release because it deploys the app. Maintain `RELEASE_NOTES.md` with every release version identifiable in the commit history and preserve its prior entries. On `dev`, record user-facing changes since the last merge into `master` under the planned next version ID; do not use an `Unreleased` section and do not require a PR to exist before adding notes. Keep pending notes grouped under that version as changes accumulate. If a release is abandoned or its intended version changes, preserve the notes and update the heading to match the next release that will merge. Only when the release PR merges into `master` should the About version and startup release notice be updated; retain at least the previous published startup notice.
- On `dev`, if the pending release notice is shown, use the same planned version ID as the `RELEASE_NOTES.md` heading, never “Unreleased changes.” Keep its content consistent with the notes and do not imply that the version is already published; update its notification-dismissal ID when the planned version changes.
- Keep application logic in the existing ES modules under `js/`; `js/javascript.js` is generated by `npm run build`.
- For integrated-browser checks that need history, automatically seed `test/fixtures/sample-history.js` before testing. Generate date-specific records with `node --input-type=module -e 'import { createSampleHistory } from "./test/fixtures/sample-history.js"; console.log(JSON.stringify(createSampleHistory(), null, 2))'`. Before loading or reloading the app, snapshot all localStorage entries, set `autoend` to `false`, set `nosave` to today's local date, and seed a current-day record with a deterministic future end time (for example `StartDec: "9.00"`, `TotalDec: "8.00"`, `TotalNoBreakDec: "8.00"`, `OvertimeDec: "0.40"`, `HourSchedule: "7.60"`, and `Summary: "Browser test"`). This prevents the end-of-day easter eggs from triggering or the app from replacing the test end time with the current time. Then seed the date-specific history fixture. Use an isolated browser context when available; otherwise restore the original localStorage entries in a `finally` block after testing. Prefer injecting into the already-loaded page and refreshing its history UI without a reload. Never leave fixture records in the user's persistent browser profile.
- Run `npm test` and `npm run build` for JavaScript changes. Validate OpenSpec changes with `npx @fission-ai/openspec validate --all --strict --no-interactive`.
